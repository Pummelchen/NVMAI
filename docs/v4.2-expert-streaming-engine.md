# NVMAI v4.2 expert streaming engine

v4.2 is an incremental control-plane investigation on top of the v4.1
hit/fixup runtime. It does not change model semantics, the `.gturbo` format,
quantization representation, prefill scheduling, KV storage, or server API.

Status terms in this document are literal:

- **default**: used without an experimental environment variable;
- **implemented, experimental**: built and tested but not selected by default;
- **rejected**: implemented far enough to measure, then removed or left out of
  the decode path because it stalled, regressed throughput, or increased memory;
- **planned**: not represented as working production behavior.

## v4.1 source assessment

Inspection of tag `v4.1` (`3868a16`) confirmed this decode sequence:

```text
attention + router GPU commands
  -> host waits for router completion
  -> host reads eight top-k IDs
  -> serial streamer lookup + locked cache plan
  -> host partitions hit/miss positions
  -> shared expert and resident routed phase 1 are committed
  -> RDADVISE bookkeeping
  -> a global-queue job enters the blocking expert reader
  -> Swift continuation resumes after all bytes arrive
  -> host binds miss buffers and commits fixup + phase 2
```

The data plane was already sound. Exact slot generations are reserved and pinned,
resident phase 1 preserves top-k positions, the miss-only fixup writes the missing
activation rows, and common phase 2 reduces every selected expert in router order.
Prefill has a separate expert-major bounded tile scheduler.

The remaining costs were therefore control-plane costs:

- one router completion barrier and top-k readback per routed layer;
- locked cache planning and a second CPU partition pass;
- arbitrary `MTLBuffer` argument rebinding;
- delay between slot reservation and storage submission;
- a successful-I/O task wake followed by fixup encoding and submission;
- blocking `waitUntilCompleted()` in the experimental Metal I/O reader;
- one allocation and Metal object per cache slot.

## What v4.2 implements

### Split storage operations and persistent submission

`ExpertLoadOperation` separates submission from completion and exposes
`submitted`, `inFlight`, `completed`, and `failed` state. A fixed four-queue
`ExpertIOScheduler` replaces per-batch use of the process-wide global queue.
Legacy fetch entry points are compatibility wrappers over this operation.

The **immediate** experiment begins bounded pread as soon as miss slots and
generations are reserved, before hit partition/binding/encoding. The **default**
remains deferred because immediate submission was slower in the representative
real-model A/B.

### Event-driven bounded pread

The experimental event path is:

```text
reserve and pin exact slot generations
  -> submit F_NOCACHE pread into shared slot memory
  -> pre-encode and commit fixup waiting on MTLSharedEvent value N
  -> reader publishes resident metadata and success/failure status
  -> reader signals N
  -> Metal releases the already-submitted fixup
```

One model-wide monotonically increasing timeline is used. Out-of-order read
completion cannot advance over an earlier unfinished value. Status words are
allocated in 4,096-entry, 16 KiB chunks, capped at 64 MiB, so thousands of batches
do not create thousands of tiny Metal buffers. Values and status words are never
reused; exhaustion fails explicitly instead of wrapping.

Failure also advances the timeline with a failed status. Event-specialized phase
1 and phase 2 kernels check that status before reading expert bytes; phase 2 emits
the safe residual value, the command retires, and the stored I/O error is then
propagated to the request. A failed pread therefore neither consumes partial bytes
nor strands a command buffer behind an event that can never signal. The status
branch is compiled out of the default kernels with a Metal function constant.

This removes the successful-I/O task wake/encode/commit bubble. It does not remove
the true next-layer dependency: the host can still wait for the event-gated routed
command when the following layer needs its output.

### Nonblocking Metal I/O API

`MetalExpertReader.beginFetch` commits `MTLIOCommandBuffer` work and completes by
callback; its decode API no longer calls `waitUntilCompleted()`. It can encode a
native status copy and shared-event signal, and the isolated file-to-buffer event
test passes.

Native MTLIO-to-compute event chaining was **rejected for v4.2**. On the
qualification M3, a compute command pre-submitted against an in-flight MTLIO
destination reproducibly stopped making progress. The Metal backend therefore
keeps a host dependency and remains experimental. Production remains bounded
`F_NOCACHE` pread.

### Contiguous per-layer expert pool

`NVMAI_EXPERT_CACHE_LAYOUT=pool` allocates one 2 MiB-aligned shared allocation per
opened layer. Slot offsets are VM-page aligned and use the exact page-rounded
expert stride; pread and Metal I/O target the slot pointer/offset directly.
Argument buffers bind the pool with slot offsets, so there is no copy.

The pool preserves the configured byte count, generation, state, and pinning
rules. It remains **experimental** because a single large `bytesNoCopy` Metal
resource caused substantially more whole-machine memory to become unavailable
than separate slot resources even when process RSS was similar. The initial
2 MiB-per-slot padded form was removed after making this effect worse.

### GPU-visible residency and compact classification

Every layer exposes a 16-byte-per-expert shared table:

```text
expert -> slot, EMPTY|LOADING|RESIDENT, generation
```

Publication order is reserve, increment generation, publish `LOADING`, fill all
bytes, publish `RESIDENT`, then signal the event. Eviction removes the old expert
mapping before a new load is published. Existing leases pin the exact generations
until all consuming GPU commands retire.

`NVMAI_DECODE_EXPERT_EXECUTION=gpu-residency` runs a Metal classifier immediately
after top-k selection and emits only hit positions, miss positions, miss expert
IDs, resolved slots, and generations. Loading or stale/empty entries are misses.
The CPU plan remains eviction authority and must agree with the GPU classification
or the request fails closed.

This classifier is **implemented, experimental**, but it is not the requested
CPU-free all-hit implementation. The host still waits for router completion,
plans/pins slots, and binds the consuming buffers. A subsequent pool-addressed
resident-hit kernel was implemented and removed after its real-model command
stopped making GPU progress. Shipping it would have replaced a measured working
path with a hang.

### Cache policy and telemetry

`NVMAI_EXPERT_CACHE_POLICY=aging-lfu` halves use counts every 1,024 plans. LRU and
lifetime LFU remain available; LFU stays the default because aging did not produce
a measurable representative improvement.

`NVMAI_RUNNER_STATS=1` adds per-token router-readback, cache-plan, I/O queue,
completion-to-fixup-submit, host-wait/avoided-wait, GPU classification, and all-hit
layer counters. Existing cache, bytes, latency histogram, hidden-I/O, and reload
metrics remain. `NVMAI_KERNEL_STATS=1` reports per-role GPU spans, merged occupancy,
and the largest inter-command gaps.

The exposed-I/O estimate is the miss completion tail after already-submitted useful
GPU work. It is an approximation based on host completion clocks; it is reported
separately from total I/O and never used to alter inference behavior.

## Production and experimental controls

The measured production combination is unchanged from v4.1:

```text
NVMAI_DECODE_EXPERT_EXECUTION=hit-fixup
NVMAI_EXPERT_IO_BACKEND=pread
NVMAI_EXPERT_IO_SYNC=host
NVMAI_EXPERT_IO_SUBMISSION=deferred
NVMAI_EXPERT_CACHE_LAYOUT=per-slot
NVMAI_EXPERT_CACHE_POLICY=lfu
```

Unset variables select those values. Supported qualification alternatives are:

```text
NVMAI_DECODE_EXPERT_EXECUTION=barrier|hit-fixup|gpu-residency
NVMAI_EXPERT_IO_BACKEND=pread|metal
NVMAI_EXPERT_IO_SYNC=host|event
NVMAI_EXPERT_IO_SUBMISSION=deferred|immediate
NVMAI_EXPERT_CACHE_LAYOUT=per-slot|pool
NVMAI_EXPERT_CACHE_POLICY=lru|lfu|aging-lfu
```

Unknown values fail closed. Event synchronization implies immediate bounded-pread
submission. Metal I/O is deliberately excluded from the event decode path after
the cross-queue stall described above.

## Real-device results

Final control-plane qualification used the release build, Ornith 1.5 35B-A3B
8-bit, 8 GiB expert budget, native 262,144 context, 8-bit KV, MTP/thinking/concise
off, prompt cache on, temperature 0.6, top-p 0.95, top-k 20, presence penalty 0,
seed 41, and 128 generated tokens. Each case used a fresh server and identical
cold/warm requests. All response strings matched exactly.

Machine: base M3 (4P+4E), 24 GB; macOS 26.6.2; Swift 6.3.3.

| Case | Cold tok/s | Warm tok/s | I/O hidden cold | Host waits avoided cold | Machine free after warm |
| --- | ---: | ---: | ---: | ---: | ---: |
| production deferred/per-slot | **6.907** | **8.002** | 12.85% | 0 | 50% |
| event pread/per-slot | 6.747 | 7.811 | 20.73% | 3,315 | 52% |
| event pread/pool | 6.710 | 7.898 | 16.61% | 3,315 | 33% |
| GPU classifier + event pool | 6.835 | 7.931 | 17.37% | 3,315 | 33% |

The event bridge does what it claims—zero successful-I/O host waits and zero
completion-to-fixup submission delay—and its compact status storage restores
bounded memory. It still loses 2-3% throughput because the dependency simply moves
into longer GPU/next-layer waits. Pool/GPU cases do not justify their whole-machine
memory cost. The production default therefore stays on the simpler v4.1 schedule.

The archived v4.1 release binary measured 6.906 tok/s cold and 7.988 tok/s warm in
the same short workload. The final default specialization measured 6.907/8.002,
showing no production decode regression within run-to-run noise.

The broader four-model/prompt matrix was intentionally not spent after the
representative architecture failed its promotion criteria. This follows the stop
rule: do not multiply expensive measurements for a path that already loses and is
not becoming default. The script can reproduce broader runs when a future design
removes the remaining router/readback dependency.

Raw JSON and logs are written to `.build/benchmark-results/` and
`.build/benchmark-logs/` (git-ignored). Reproduce the final A/B with:

```bash
python3 benchmark/nvmai_v42_control_plane_ab.py --prompt short
```

## Correctness and safety evidence

- `swift test --no-parallel`: 775 tests in 136 suites passed.
- `tools/lint.sh`: force-cast, function-length, and unchecked-Sendable gates pass.
- `swift build -c release`: succeeds.
- `tools/golden-baseline.sh --check 4`: Ornith 4-bit output is byte-identical to
  the stored greedy baseline.
- Final Ornith 8-bit A/B: all cold/warm response strings match across production,
  event, pool, and GPU-classifier modes.
- Synthetic tests cover operation state/failure, monotonically increasing and
  out-of-order event values, failure signalling, direct Metal event loads, pool
  offsets/no overlap, loading/resident/evicted GPU classification, failed-read
  cleanup, pinned generation lifetime, and concurrent cache churn.

No page-cache-assisted backend is silently selected. Prefill remains on the v4.1
grouped/tiled path, and the default routed kernels compile the event status guard
away.

## Rejected and deferred work

- **Rejected:** native Metal-I/O event-gated compute on this M3 (cross-queue stall).
- **Rejected:** pool-addressed all-hit phase-1 kernel (real-model GPU progress
  stopped).
- **Not promoted:** immediate submission, event pread, contiguous pool, GPU
  classifier, and aging LFU (no end-to-end win under the representative run).
- **Deferred:** adaptive per-layer budgets and GPU-managed eviction. Moving LFU to
  Metal is not justified while CPU planning is about 1.0-1.2 ms per token and the
  attempted end-to-end GPU path is not safe.
- **Deferred:** speculative routing. Exact deterministic stalls were addressed
  first, and previous-token prediction still describes experts already resident.

## Remaining bottleneck

v4.2 proves that removing a Swift I/O wake alone is insufficient. The next useful
design must remove the router completion/readback and buffer-binding dependency
without introducing a cross-queue resource stall or wiring the complete cache pool.
Until Metal scheduling behavior permits that safely, the v4.1 host/deferred path is
the measured production optimum on this Apple Silicon system.
