# v4.2 Experiments

This document records the v4.2 control-plane experiments and later v4.2.1
data-plane probes. It is an engineering qualification record, not a list of
enabled features. NVMAI's production path remains the measured v4.1-style
schedule: **hit/fixup, bounded F_NOCACHE pread, host synchronization, deferred
submission, per-slot cache, LFU**.

## Scope and invariants

The experiments retained the existing `.gturbo` format, exact top-8 routing,
expert ordering and quantization, shared-expert path, phase-2 reduction,
slot generations and leases, and the separate prefill scheduler. No experiment
was accepted unless fixed-seed output matched the reference and the configured
expert-cache budget remained bounded.

## Qualification setup

Primary qualification used a base M3 MacBook Pro (8-core, 24 GB), macOS 26.6.2,
Swift 6.3.3, release builds, Ornith 1.5 35B-A3B 8-bit, an 8 GiB expert budget,
native 262K context, 8-bit KV, prompt cache on, MTP/Thinking/Concise off, and
temperature 0.6, Top-P 0.95, Top-K 20, presence penalty 0.0, seed 41. Every
case used a fresh server and matching cold/warm requests.

## Results

| Experiment | Cold tok/s | Warm tok/s | Outcome |
| --- | ---: | ---: | --- |
| Production deferred pread / per-slot | **6.907** | **8.002** | Default |
| Event-driven bounded pread / per-slot | 6.747 | 7.811 | Correct; slower |
| Event-driven bounded pread / pool | 6.710 | 7.898 | Correct; more whole-machine memory pressure |
| GPU residency classifier + event pool | 6.835 | 7.931 | Correct; still needs host planning/binding |

The event route avoided successful-I/O host wakeups and submission bubbles, but
on this M3 its shared-event dependency increased the GPU/next-layer wait enough
to lose 2–3% end-to-end throughput. It is experimental, not the default.

The current default also has a small all-hit cleanup: once a plan has no misses,
it uses the already-pinned resident buffers directly rather than creating a
completed I/O ticket and resuming an async continuation. A later 64-token
Ornith 8-bit warm run recorded 1,456 avoided host waits. This does not remove the
router readback or make the all-hit path GPU-only.

## Metal I/O results

Metal I/O was tested because it can submit a file-to-buffer operation without a
host `waitUntilCompleted()`. It is not production-ready for NVMAI's bounded
streaming use case.

| Backend / synchronization | Ornith 4-bit decode | Result |
| --- | ---: | --- |
| Bounded pread / host / deferred | **16.211 tok/s** | Reference |
| Staged Metal I/O / event / immediate | 10.876 tok/s | Byte-identical, about 33% slower |
| Metal I/O, 4 commands | 11.538 tok/s | Slower than pread |
| Metal I/O, 8 commands | 11.021 tok/s | Slower than pread |

Direct Metal-I/O-to-cache execution was rejected after a resource-ownership
stall on the qualification M3. A fixed staging ring avoids that hazard and is
correct, but adds a GPU copy and has higher sparse-read latency. A later
multi-command, per-load-event/status-reduction prototype passed isolated tests
but produced different full-model Ornith tokens; it was removed and is not a
runtime control.

## Other rejected experiments

- **Immediate pread submission:** correct but slower than deferred in the
  representative real-model run.
- **Contiguous cache pool:** correct but caused substantially greater
  whole-machine memory pressure than per-slot buffers.
- **GPU residency classification:** correctly classified hits and misses, but
  did not eliminate host router readback, victim selection, or argument binding.
- **Aging LFU and LRU:** no repeatable gain over LFU.
- **8-bit fused routed-kernel prototype:** correct but slower than the generic
  affine path (6.18 vs 6.41 tok/s in the qualification probe).
- **Routing-aware slot redistribution:** improved hit rate (87.6% to 88.1%) but
  slowed the 8-bit warm run (8.30 to 7.62 tok/s), so it was removed.

## v4.2.1 data-plane probes — unpromoted

These probes tested whether redundant activation reads inside decode GEMVs and
MoE kernels could provide a >=10% end-to-end gain over v4.1. They preserved the
production bounded-SSD architecture and exact affine FP32 accumulation. All
trial code was removed after measurement.

| Probe | 4-bit result | 8-bit result | Outcome |
| --- | ---: | ---: | --- |
| Cooperative routed INT4 phase-1 activation copy | 14.764 → 14.999 tok/s (+1.6%) | — | Correct, but far below promotion gate |
| Routed/shared INT8 activation staging | — | 7.808 → 7.768 tok/s | Slower; threadgroup memory reduced occupancy |
| Tiled routed phase-2 (4 output dimensions) | — | 7.808 → 7.832 tok/s (+0.3%) | Within variance; not promoted |
| Staged affine attention/GDN GEMV | — | 7.808 → 7.777 tok/s | Slower; threadgroup staging lost to occupancy |
| Direct INT8 byte-pair affine GEMV | — | 7.808 → 7.875 tok/s (+0.9%) | Correct, but within variance and below gate |

The 8-bit control showed attention/QKV/GDN work as the largest GPU role, so
the last two probes targeted that path rather than sparse expert I/O. Neither
reduced time to first token in a qualified way: 8-bit `prefill_s` was generally
higher than the v4.1 control. The single 4-bit prefill observation was not an
interleaved, fixed-seed result and is not evidence of a TTFT improvement.

These exploratory runs used the user-facing sampling defaults but did **not**
set a fixed request seed or complete the required interleaved multi-run
qualification. Consequently, they establish rejection evidence only; they do
not change the published v4.1 benchmark, defaults, or release status.

## Validation

- Full serial package tests passed.
- `tools/lint.sh` passed.
- Release build passed.
- `tools/golden-baseline.sh --check 4` produced byte-identical Ornith 4-bit
  output.
- Real-model comparisons rejected any output mismatch; no failed experiment was
  promoted merely for higher apparent throughput.

## Conclusion

v4.2 showed that removing a Swift wake alone is not enough: on this hardware the
remaining critical path is sparse SSD miss latency plus the serialized
router/readback/buffer-binding chain. The next viable improvement must reduce
that chain without a cross-queue Metal resource hazard or an unbounded OS file
cache. Until then, the production pread hit/fixup path is the fastest validated,
bounded-memory configuration.

For the detailed source-level design and reproducible commands, see
[v4.2 expert streaming engine](v4.2-expert-streaming-engine.md).

## v4.3 predictive prefetch — experimental, not promoted

v4.3 tested a narrower idea than the rejected v4.2 control-plane work:
predict a future layer's routed experts, read their raw bytes into a small
separate staging ring, and adopt a completed entry only when the exact router
later selects it. Predictions never alter top-8 routing, weights, ordering,
quantization, or cache-slot generations.

The experiment is disabled by default. It can be enabled only for measurement:

```bash
NVMAI_PREDICTIVE_PREFETCH=1 NVMAI_PREFETCH_TOP_M=4 \
  .build/release/NVMAICLI ...
```

The ring has four raw shared-memory buffers at top-M 4. They are not cache
slots, so an incorrect read cannot evict or publish an authoritative expert.
The bounded `F_NOCACHE` pread service gives queued demand work precedence over
queued speculative work. An in-flight speculative read is never treated as
valid data; the normal exact-demand path remains the fallback.

### Predictor evidence

The probe used a 128-token continuous-prose decode with Ornith 1.5 4-bit,
64 expert-cache slots per layer, native 262K context, 8-bit KV, MTP off,
Thinking off, and greedy decoding. The useful measure is recall of **actual
nonresident misses**, not raw route overlap.

| Predictor | Candidate count | Actual nonresident-miss recall | Precision | Decision |
| --- | ---: | ---: | ---: | --- |
| Online layer-transition prior | 8 | 3.25% | 49.5% | Rejected: too few demand reads can be hidden |
| Next layer's real router on current normalized residual | 4 | 32.6% | 79.7% | Implemented as the conservative staging probe |
| Next layer's real router on current normalized residual | 8 | 64.1% | 56.4% | Useful signal, but too much speculative traffic for promotion |

Raw top-k agreement was misleading: the transition prior reached 44.2% at
top-8 while helping only 3.25% of real cache misses because most predicted
experts were already resident. The model-aware probe is materially better,
but its one-layer lead time remains short.

### End-to-end result

Two interleaved fresh-process 128-token runs per side used the same continuous
prose prompt, bounded production pread/hit-fixup configuration, 64 slots per
layer, 8-bit KV, native context, greedy decoding, and top-M 4. These are
rejection measurements, not a replacement for the published 512-token v4.1
benchmark.

| Quantization | Prefetch off runs | Prefetch on runs | Median change | Outcome |
| --- | --- | --- | ---: | --- |
| 4-bit | 9.924 / 5.944 tok/s | 10.048 / 5.193 tok/s | **-3.9%** | Rejected |
| 8-bit | 5.095 / 5.005 tok/s | 5.879 / 5.006 tok/s | **+7.8%** | Below +10% gate |

The run order was off/on/off/on. Thermal state changed materially during the
sequence, which is why the median—not the best individual sample—decides the
result. The latest one-off text-generation probe with the feature enabled
recorded 9.098 tok/s at 4-bit and 4.855 tok/s at 8-bit. It used a different
run condition and is not comparable with the published v4.1 medians of 16.45
and 8.75 tok/s.

### Why it did not qualify

- **Transition-only prediction failed:** it predicted mostly already-resident
  experts, so it could not remove meaningful demand I/O.
- **Model-aware prediction was late:** it becomes available after the current
  layer's post-attention normalization, leaving only one layer of useful work
  in which to hide an SSD read.
- **Speculative I/O still has a cost:** even with demand-first queueing, an
  active pread cannot be preempted. At top-M 4 the 4-bit median regressed; at
  8-bit the repeatable gain remained below the required 10%.
- **No valid v4.1 replacement result exists:** published v4.1 used a different
  512-token warmup-and-three-run protocol, sampling defaults, and prompt-cache
  settings. Comparing those numbers directly would be invalid.

### Validation

- Release build passed.
- Full serial `swift test --no-parallel` passed.
- `tools/lint.sh` and `git diff --check` passed.
- `tools/golden-baseline.sh --check 4` produced byte-identical Ornith 4-bit
  output.
- A direct greedy prefetch-off versus prefetch-on 4-bit run was byte-identical.
- The staging cache test verifies that `LOADING` entries are never reported as
  resident; the Python trace-analysis test verifies miss-recall accounting.

The current experiment is retained only as an opt-in research path. The next
credible step is a two-stage predictor with explicit completion, demand-join,
and exposed-I/O telemetry. It must clear the same fresh, matched +10% gate for
both 4-bit and 8-bit before it can replace v4.1 production scheduling.
