# NVMAI post-v4.6 optimization inventory

Status of the eight items identified after the v4.6 release. Four are
implemented and merged, two are closed on evidence without building what they
proposed, and two are not started. **Throughput qualification for the merged
items is still outstanding** — see "Pending measurement" at the end.

Baseline for every figure below: M3, 24 GB, macOS 26.6.2, the published
512-token continuous-generation protocol (4-bit 22.53 tok/s, 8-bit
9.40 tok/s) and the 6,103-token prefill workload, all measured on a
verified-idle machine.

## The decode token, after v4.6

| | 4-bit | 8-bit |
| --- | ---: | ---: |
| token | 60.04 ms (instrumented) | 119.39 ms |
| GPU busy | 28.20 ms | 50.27 ms |
| exposed expert I/O | 8.50 ms (14.2%) | 36.87 ms (30.9%) |
| expert GPU compute | 7.96 ms | 13.45 ms |
| expert bytes read | 31.4 MiB/token | 128.1 MiB/token |
| **effective read bandwidth** | **3.61 GB/s** | **3.39 GB/s** |
| cache hit rate | 94.31% | 87.70% |

The bandwidth row is the load-bearing one; see item 7.

## Item 1 — ANE model preload · SHIPPED

The ANE path reloaded a Core ML model per layer-chunk (~0.5 s), serialized in
front of the next prediction. It now preloads the next covered layer as soon
as the current prediction returns, overlapping the MoE stage that follows.
At most one preload is outstanding and it becomes resident only at the moment
the previous model is dropped, so the one-arena rule that keeps the expert
cache in RAM is intact.

## Item 2 — 8-bit ANE prefill · SHIPPED (exporter fix + sidecar)

This was scoped as "zero new code" and that was wrong: the exporter hardcoded
4-bit nibble unpacking, while 8-bit attention weights are one byte each. It
would have silently misread every weight. The exporter now reads `weightBits`
from the manifest and handles both. The 8-bit sidecar is exported (541 MB,
`sourceWeightBits: 8`) and loads; its throughput is not yet qualified.

## Item 3 — chunk-1024 ANE variants · NOT STARTED

Would extend ANE prefill coverage below 4,096 tokens, where the sidecar
currently declines because padding a short prompt to a full chunk costs more
than the whole GPU prefill. Needs an exporter chunk parameter and runtime
support for more than one chunk width.

## Item 4 — MoE prefill tiles · NOT STARTED

After the ANE path removes the attention block, the routed-MoE tiles become
the largest single prefill cost. From the 6,103-token GPU profile the per-role
totals were attention 84.3 s, MoE tiles 27.6 s, GDN 13.3 s, shared expert
6.1 s; with attention offloaded the tiles are roughly half of what remains.
They have never been profiled with GPU counters, and the standing explanation
for the ~435 GFLOP/s they achieve is 4-bit dequant ALU cost — the same wall
prefill hit everywhere else. Worth one counter profile before any kernel work.

## Item 5 — sidecar integrity · SHIPPED, design corrected

The proposal was to cover the sidecar in the model's install receipt. That is
wrong: the receipt attests the *downloaded* payload and is bound to the
manifest, while the sidecar is generated afterwards by a local tool. Adding it
would have broken the receipt's meaning and its moved-directory semantics.

The real risk is a sidecar exported from *different weights* — it computes
plausible-looking but wrong attention and nothing downstream would catch it.
So the sidecar records the manifest digest of the `model_weights.bin` it was
built from, and the runtime refuses a mismatch. The manifest is itself
receipt-bound, so its digest is a trustworthy identity. With no digest
available the runtime says the binding is unverified rather than trusting it
silently.

## Item 6 — tiled softmax · SHIPPED

The softcap+softmax front-end was still running two full-vocabulary passes in
a single 256-thread threadgroup — the same pathology the Top-K half lost in
v4.6. It is now a tiled reduction (4,096-entry tiles → (max, sum-of-exp)
pairs → merge → device-wide normalize), selected by the existing
`NVMAI_SAMPLER_PATH` control so an A/B still measures both halves of the
sampler. Pinned against the single-threadgroup form at the production
vocabulary and at tile-boundary sizes; worst elementwise difference < 1e-5.

## Item 7 — 8-bit expert I/O · CLOSED: the SSD is already saturated

Expert I/O is 30.9% of the 8-bit token and only 14.5% of it is hidden, which
made it look like the largest remaining decode target (Amdahl bound 1.45x).
It is not reachable, and the reason is a single number:

> **8-bit expert reads run at 3.39 GB/s; 4-bit at 3.61 GB/s. The measured
> device ceiling for expert-sized random reads on this machine is
> ~3.2–3.9 GB/s.** The storage path is already at the wall.

That closes the scheduling family retroactively and completely. The twenty
v4.2/v4.3 experiments — event synchronization, submission timing, pool
layout, GPU residency classification, Metal I/O, predictive prefetch — were
all trying to schedule a device that had no idle capacity to schedule. They
did not fail on engineering; they were aimed at a resource running at 100%.

The two other levers are also closed:

- **Hit rate.** 87.70% against a 93.6% ceiling for *any* replacement policy
  (7,808 of 122,560 activations are first-touch). The 5.9 points are
  purchasable only with slots, i.e. RAM, and large budgets are a measured
  trap: 8-bit at a 16 GiB budget collapses to 0.46–1.22 tok/s.
- **Bytes per miss.** Fixed by the weight format — unless the format changes.

### The one option that remains, and it is a format decision

A **mixed-precision build — 8-bit attention, 4-bit routed experts** — is
already expressible: `manifest.quant` carries independent `weightBits` per
slot (`attention`, `embedding`, `router`, `sharedExpert`, `routedExpert`),
and the runtime reads them. Routed experts at 4-bit is exactly what the
shipping 4-bit model already does.

Modeled from the measured rows above (8 GiB budget → 128 slots at the 4-bit
stride, so 4-bit's hit rate and per-token expert bytes apply, while attention
stays 8-bit):

| | today (8-bit) | modeled mixed |
| --- | ---: | ---: |
| exposed expert I/O | 36.87 ms | ~8.50 ms |
| expert GPU compute | 13.45 ms | ~7.96 ms |
| GPU busy | 50.27 ms | ~44.8 ms |
| token | 119.39 ms | ~85.5 ms |
| **throughput** | 9.40 tok/s | **~11.7 tok/s (+24%)** |

This is a **model, not a measurement**, and it assumes the non-I/O idle
(32.25 ms) is unchanged. What it needs is a down-quantizer in the repacker
(the installer currently streams a uniformly-quantized source checkpoint, so
8-bit→4-bit expert conversion is new lossy work) plus a quality
qualification. That is a product decision about what "8-bit" promises, not a
runtime optimization.

## Item 8 — 3-bit weights · CLOSED: fails both gates

Two questions decided it, both answered from the installed weights with no
runtime code (`benchmark/nvmai_3bit_probe.py`).

**Quality: fails.** Affine round-trip error (group 64, the format NVMAI uses)
on real attention and shared-expert tensors:

| tensor | 3-bit | 4-bit | ratio |
| --- | ---: | ---: | ---: |
| L3 q_proj | 0.2120 | 0.0198 | 10.70x |
| L3 o_proj | 0.2157 | 0.0204 | 10.58x |
| L3 shared gate_proj | 0.2309 | 0.0218 | 10.57x |
| L19 q_proj | 0.2135 | 0.0203 | 10.53x |

Median **10.56x** the 4-bit error. The weights already carry ~2% relative
error at 4-bit; 3-bit takes them to 21–24%.

**Packing: also weak.** 3 bits does not divide a 32-bit word, so the nominal
25% saving does not survive:

| bits | bytes/64-weight group | vs 4-bit | power-of-two |
| ---: | ---: | ---: | --- |
| 3 (bit-exact stream) | 28.0 | 0.778x | **no** |
| 3 (word-padded) | 32.0 | 0.889x | **no** |
| 4 | 36.0 | 1.000x | yes |
| 6 (withdrawn) | 52.0 | 1.444x | no |

So the real saving is 22% at best, and only via the cross-word extraction
path that costs extra ALU per weight — and NVMAI's own precedent for
non-power-of-two packing is 6-bit, measured at 46.8 GB/s against 60 for both
4-bit and 8-bit, and withdrawn for exactly that reason.

**Verdict:** at best 22% fewer bytes for 10.6x the weight error, using the
packing family that already cost this project a format. No repacker, kernel,
or receipt work was written. If a lower-precision build is ever wanted, the
honest path is validating a community-quantized checkpoint's *output quality*
first, not building the packing.

## Pending measurement

These are implemented and correctness-tested but **not yet qualified for
throughput**:

- item 1 (ANE preload) — its effect on prefill is unmeasured;
- item 2 (8-bit ANE prefill) — the sidecar exports and loads, but no valid
  A/B exists;
- item 6 (tiled softmax) — pinned numerically against the original kernel,
  but its decode gain is unmeasured.

An attempted sweep produced 4-bit and 8-bit figures that are **discarded, not
reported**: the machine was running a browser at 117% CPU and other
applications, the GPU sat at 57% before launch, and the worst-affected run
reported an expert cache hit rate of 0.277 against a normal 0.877 — the
signature of the slot cache being pushed out of RAM, which looks exactly like
a code regression and is not one.

Two methodology fixes came out of that:

- **The benchmark prompt is now pinned.** It was built from `README.md` and
  `AGENTS.md`, so editing those files silently changed the prompt from 6,103
  to 6,593 tokens between sweeps and, with attention quadratic in length,
  made the two non-comparable.
- **The preflight now refuses a loaded machine**, not just a busy GPU: it
  checks other processes' CPU, free memory, and swap in use. GPU utilization
  alone did not catch this.
